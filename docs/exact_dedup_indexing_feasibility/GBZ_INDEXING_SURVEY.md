## What mapping to GBZ buys, and what it does not

Start with the negative, because it governs everything else. **Mapping to a GBZ does not remove `vg prune` or GCSA2.** `vg mpmap` hard-exits without `-g` (`src/subcommand/mpmap_main.cpp:1633-1635`, and `src/log.hpp:29-30,61-62` shows `logger.error()` calls `exit()` on destruction), and all three seeders — `find_mems_deep`, `find_fanout_mems`, `find_stripped_matches` at `src/multipath_mapper.cpp:707-723` — are GCSA2 queries, as is the splice scorer at `:3801`. Nothing in `mpmap_main.cpp`, `multipath_mapper.*` or `mapper.*` mentions minimizers, gbwtgraph or GBZ. So chr2's **12:47:16 at 341.07 GiB** prune and the GCSA2 build behind it stay on the critical path. Only switching mapper removes them, and upstream's shipped GBZ-RNA route (`vg autoindex --workflow lr-giraffe` + `vg giraffe`) is long-read, single-path, and cannot discover novel junctions — which is the object of this fork's splice investigation.

What GBZ permission does reach is four stages: **strip, the guide GBWT, the XG, and the distance index** — plus a partial bite out of the XG that `vg prune -u` builds inside itself.

## Ranked by measured saving

**1. Drop `-r/--add-ref-paths` from `vg rna`, eliminating the strip stage.** Saves the whole strip stage, measured on chr2 at **1:54:12 and 213.80 GiB** (`docs/gbwt_creation/README.md`), and empties the path payload from the XG that prune builds in-process — the phase that is **33.2%** of chr2's 12:47:16 and holds the **336.89 GiB** path plateau (`docs/prune_scheduling/README.md:45-51`). The XG build itself is not eliminated; `src/subcommand/prune_main.cpp:479-513` constructs it unconditionally in restore/unfold mode, as I confirmed reading the file. How much of that 6.19 h is path-dominated was never measured, so no fraction is claimed. *Supported today*, but on a 37-node fixture only: stripped and unstripped arms gave identical `vg stats -N -E -l` (40/34/224), identical node-sequence and outdegree multisets, but **different duplicate node IDs** (49 vs 50, 43 vs 41) and a different `.mapping`. Acceptance must run the fork's relabel-invariant digests, not `cmp`.

This is not a standalone win, and the dossier never says so: dropping `-r` **forces** the GBZ route. With no embedded paths, `vg gbwt -E` has nothing to index, so the guide must come from `vg rna -b -g`; and an XG built from a pathless genic.pg is useless to mpmap. The three "works today" findings are one change seen from three sides.

**2. Replace the separate guide-GBWT stage with `vg rna -b -g`.** Removes one stage and one full re-read of chr2's **173.58 GB** transcript_full.pg. The stage being replaced measured **3:15:11 at 229.23 GiB** on chr2 — but that is not the saving: it was produced by the private `vg-gbwt-insertion-threads` binary at `--num-jobs 24`, whereas `Transcriptome::add_transcripts_to_gbwt` is a serial `gbwt_builder->insert` loop (`src/transcriptome.cpp:3998-4023`). Net wall change is **unmeasured and could be negative**, and vg rna's peak rises by the DynamicGBWT cost for chr2's 29,902,979 paths — which is the opposite of what this fork's `vg rna` memory work achieved. *Supported today*; fixture-verified byte-identical graph and byte-identical pruned output. Two contract breaks: `-g` is mandatory or GBZ construction aborts with `InvalidGBWT`, and the metadata shape changes (`vg paths -L -g` prints `tx1_R1#0#0#0` instead of `tx1_R1`), so the production `guide_check` `cmp` fails as written.

**3. Build the XG as a GBZ instead — build-side win, runtime loss as currently built.** On chr21 exact, same genic.pg: `vg index -x` took **54:28.44 at 68.52 GiB** producing **55,013,545,597 B**; `vg gbwt -g` took **3:30.59 at 46.35 GiB** producing **622,882,936 B**. That is **88.3x** smaller and **15.5x** less wall per chromosome. mpmap accepts it today — `mpmap_main.cpp:1758` is `load_one<PathHandleGraph>` with no XG constraint, and "Graph is not in XG format" is cosmetic, emitted inside `if (!suppress_progress)`.

But the runtime is a loss, and I can now say why with a completed run the dossier under-used. `/mnt/ssd/lalli/.claude/jobs/6a731a8b/tmp/gbz_fixture/mpmap_ref.time.txt` records `vg mpmap -x chr21.ref.gbz -g chr21.gcsa -t 4` finishing **exit 0 in 27:29.23 at 162,068,556 KB = 154.56 GiB** to map **5 reads**. Of its 27.2 minutes of startup, **14.3 minutes** (3.3 m → 17.6 m) are `overlay_helper.apply()` at `mpmap_main.cpp:1830-1831`. The companion run against untagged `chr21.gbz` was killed by signal 15 at 11:36.55 at 147.83 GiB, still inside the same phase.

The mechanism is settled, and here the dossier is internally wrong. gbz-topology-fidelity claims chr21.gbz's walks are haplotype-sense, that the overlay is therefore not the explanation, and that the ref.gbz run "was observed at 63 GB". I counted directly: `vg paths -x chr21.gbz -L` gives **1,398,636 REFERENCE, 4,209,052 GENERIC, 0 HAPLOTYPE**. `ReferencePathOverlay` indexes exactly REFERENCE and GENERIC (`deps/libbdsg/bdsg/src/reference_path_overlay.cpp:31-32`, which I read), so it indexes **all 5,607,688**. The 63 GB figure was an in-flight observation, not the 154.56 GiB peak in the receipt. The overlay is the mechanism.

And the cost is this project's own artifact, not GBZ's. `get_sample_sense` (`deps/gbwtgraph/src/utils.cpp:174-188`) is three lines: the magic generic sample → GENERIC, a sample in the reference-samples tag → REFERENCE, everything else → HAPLOTYPE. The 4,209,052 GENERIC paths are the `__panSC_retention_pad1000__<sha>_L_R1` walks, generic purely because their names carry no PanSN `#` fields; the REFERENCE ones are PanSN transcripts like `NA21110#1#NA21110_ha_T0366374_R1` under a reference-samples tag. **The target is a GBZ whose REFERENCE/GENERIC set is exactly the chromosome reference and nothing else.** That is a naming-and-tagging change at the guide-GBWT stage, not a vg code change — but no shipped flag reaches it (see tier b).

**4. Build the distance index from the GBZ.** This is the one **unconditional win available today**. Arm-to-arm on chr21, same pinned binary, same options: from the GBZ **2:31.32 at 8.06 GiB**; from the XG **3:45.47 at 60.59 GiB** — **7.5x less peak RSS and 1.49x less wall**, at 5.2x the CPU-seconds (1,010.6 vs 195.6), which is GBZ load, not parallel construction. Use the positional form; `vg index -j out.dist -x graph.gbz` fails, because `src/subcommand/index_main.cpp:778` is hard-typed to `xg::XG`, while the positional branch at `:790-806` has an explicit GBZ path — I read both. The distance index never needed an XG at all: `fill_in_distance_index` takes a bare `const HandleGraph*` (`src/snarl_distance_index.hpp:34`) and touches no path API. One run per arm, host at load 44, **no noise floor**; the 7.5x memory ratio is far outside plausible contention, the 1.49x wall ratio is not. It also deletes mpmap's `PathComponentIndex` phase — 3.5 minutes (19.0 → 22.5 m) in the completed ref.gbz run, which had no `-d`. It does not delete the overlay.

## Tiers

**(a) Works today with stock vg.** The GBZ-built distance index (#4). `vg rna -b -g` in place of the guide stage (#2). Dropping `-r` (#1) — fixture-scale only. GCSA2 built straight from a GBZ (`vg index -g out.gcsa -x graph.gbz`, verified on cactus-BRCA2), which removes chr2's 6,774,195,898 B pruned graph and 340,858,176 B mapping as GCSA2 *prerequisites* — but see the refutation below before crediting it.

**(b) Modest change in this fork.** Constructing a correctly-sensed mpmap GBZ. None of the shipped routes work: `vg gbwt -E` makes everything GENERIC; `--set-reference CHM13` gave **0** REFERENCE paths because CHM13 is not a sample in guide.gbwt; `vg rna -b` yields haplotype-sense with *no* named paths, because `cache_named_paths` returns early without contig names (`deps/gbwtgraph/src/gbwtgraph.cpp:479-484`, read). That last one makes the overlay free and is the trap: it empties `ref_path_handles` at `mpmap_main.cpp:1838`, reproducing the measured xy2 hazard — exit 0, no warning, **MAPQ 1 → 60**, secondary alignment dropped. **Any move to `-x` GBZ must be gated on a path-sense check, never on exit status.** Also in this tier: one `register_recipe` line for `{"Spliced Distance Index"} <- {GBZ}` (`src/index_registry.cpp:4038` is the sole producer); and a tool to emit the 25,251 missing edges as two-node walks and close the topology gap.

**(c) Research.** Minimizer seeding for mpmap. The insertion point exists — `--mmp-primary` replaces the MEM pool wholesale at `multipath_mapper.cpp:344-351` — but `range` and the `gcsa->count` call at `:3801` still need substitutes, the splice-rescue path is written against MEMs, and RNA seeding sensitivity would have to be re-established. There is **no upstream work to build on**: zero commits to `multipath_mapper.cpp`, `mpmap_main.cpp` or `splicing.cpp` since v1.76.1 (GitHub API, 2026-09-20), no PR, no issue, no branch, no roadmap line; mpmap's last algorithm commit is 2022-12-13. Also research: giving vg's k-mer enumerator (`src/kmer.cpp:78,114,191`) the haplotype-restricted `follow_paths` bound that makes prune unnecessary for giraffe — correctness is non-obvious, since GCSA2's prefix-doubling still permits recombination at 16-mer boundaries.

## Refutations worth knowing

**GBZ-as-GCSA2-input does not bound complexity.** The dossier called `vg stats -E` on the production GBZ "the one measurement that decides" this. It was made: chr21.gbz has **2,701,234 edges against genic.pg's 2,726,485** — a **0.926%** reduction. That is nowhere near what prune does, so the 1mb1kgp arm-D result (GCSA2 from a path-cover GBZ matched the unpruned arm to within 0.005%) holds, and **prune remains required**. The plumbing is removable; the complexity function is not.

**Swapping the in-prune XG for a GBZ is dead.** `PhaseUnfolder`'s signature invites it, but `for_each_step_on_handle` measured **325,873 µs per node** on the chr21 exact GBZ against 0.873 µs for a count-only probe.

**`vg autoindex -w mpmap` with a GBZ input silently plans prune *without* unfolding** (recipe `index_registry.cpp:3642`, confirmed by `-d`), because no recipe derives "Spliced GBWT" from a GBZ. That would remove 6.33 h of chr2's run and lose every thread-supported edge prune deletes — i.e. splice junctions. It is an annotation-policy change with an unmeasured sensitivity cost, not an indexing win.

## What this could not establish

No `vg mpmap -x chr21.xg` run exists, so **there is no controlled XG-vs-GBZ mpmap runtime comparison** — the 154.56 GiB has no baseline, only the 51.24 GiB XG file size as an upper bound on the XG side's carrier. That is the next experiment, and `chr21.xg` is already on disk. No mapper has opened either `.dist` built here. The mapping cost of the 25,251 missing edges is unmeasured, as is whether GCSA2 indexes k-mers crossing them. Drop-`-r` equivalence is fixture-scale (37 nodes vs 50.6M), and `-b -g` memory at 29.9M chr2 paths is unknown. Finally, `rpvg` appears throughout the downstream `hprc_v2_vg_rna` workspace in prepared `joint_mpmap_rpvg_*` runs, and rpvg's own `src/main.cpp:437` errors "Graph (xg format) input required" — **if rpvg stays in the pipeline, the XG is deferred, not eliminated**, and the #3 saving should not be booked. I could not confirm the intended rpvg invocation form from here.
